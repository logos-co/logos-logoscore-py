    limit  axis=consumer   PARTLY CLOSED — three consumer points now, was one
           History, kept because the reasoning is the reusable part: the matrix had ONE
           consumer driver (`py`), so a cell proved a provider agreed with the python client,
           not that two consumer surfaces agreed with each other. That hid a real defect — the
           event bridge failing to decode tagged bytes into a QByteArray was invisible because
           the undecoded map round-trips and the py client decodes the tag itself; it took
           asserting the bridge directly (logos-protocol test_event_payload_fidelity.cpp) to
           see it. It also recorded, correctly, that adding the existing C++/Rust proxies would
           NOT close the hole: both are lp/Rust-client consumers, so they share the py blind
           spot for the Qt-typed path.
           Now measured, not argued. The axis runs py + qtproxy-sync + qtproxy-async, and the
           Qt points move 22 of 172 cells — an order of magnitude more than the lp proxy's 2
           cases. Two findings came straight out of it: M3 became measurable (and is now an
           ordinary xfail), and Q1 — the Qt dispatch coercing hostile arguments — was not
           previously known at all.
           What is STILL open on this axis: * QML. No driver replays cases.json through the
           LogosQmlBridge, and the two skip[] entries describe exactly that surface. * The
           cdylib/Rust proxy. Buildable and driveable by the same --proxy-consumer flag; not
           wired in. * The lp proxy. Measured here for ATTRIBUTION (it is what proves Q1 and M3
           are the Qt style rather than the extra hop) but not carried as a standing consumer:
           it has 2 divergent cases of its own that would need registry entries first. * The
           ext table (ext-cases.json) still has no proxy at all, so its 21 cases remain
           single-consumer.
    limit  axis=transport  OPEN
           Every cell is measured over LocalSocket/QtRO: run_matrix.py builds the daemon with
           no `transports=`, and there is no flag to change it. The plain (tcp/tcp_ssl) wire is
           unreachable from this table. That mattered for uint: RpcValue's variant had no
           unsigned alternative (logos-protocol cpp/implementations/plain/rpc_value.h), so a
           uint64 above int64max wrapped to -1 there — a DIFFERENT wrong answer than the one M6
           described, which this matrix would not have matched. Fixed in the same
           logos-protocol PR as M6, but found only by reading the code: no cell here could
           reach it. The regression guard for it lives where it can run — logos-logoscore-py's
           integration table, which now carries 2^63, 2^64-1 and 2^53+1 and is replayed over
           local, tcp and tcp_ssl.

    M3  4 cell(s) in this run (4 xfail)   cases: adversarial/{tstr:any}/_bytes-key
          a one-key `_bytes` map reaching a Qt-typed map slot is reinterpreted as bytes and
          arrives EMPTY
          expected {"_bytes": "aGk"}
          got      {}   [xfail] 4 cells
          fix is: a data model where a byte string is not spelled as a map, not a stricter
          predicate — the shape that would be checked IS the encoding
    Q1  12 cell(s) in this run (12 xfail)   cases: hostile/[uint]/negative-element, hostile/[uint]/fractional-element, hostile/[int]/fractional-element
          a typed-numeric-array element is still not validated by a Qt-typed provider: the C++
          signature spells [uint] and [any] alike as QVariantList, so array-ness is the whole
          of the declared type at that layer
          expected {"__error__": "dispatch_failed"}
          got      []   [xfail] 12 cells
          fix is: consumer-side: surface the dispatch_failed envelope instead of flattening it
          to an empty container. The provider-side option previously listed here (carrying the
          LIDL element type into the Qt provider dispatch via qtArgListOf) is no longer
          pursued — see `scope`.
    Q1b  4 cell(s) in this run (4 xfail)   cases: hostile/[any]/scalar, hostile/{tstr:any}/scalar
          the Qt proxy can no longer reproduce the C++ cdylib provider's LENIENT answer for a
          non-array/non-object in a [any]/{tstr:any} slot, because its own dispatch refuses
          the argument before forwarding it
          expected 5
          got      {"__error__": "dispatch_failed"}   [xfail] cpp/qtproxy-async, cpp/qtproxy-sync
          expected "notalist"
          got      {"__error__": "dispatch_failed"}   [xfail] cpp/qtproxy-async, cpp/qtproxy-sync
          fix is: nothing, deliberately. Previously proposed: make the C++ cdylib provider's
          container decode refuse a non-array/non-object, collapsing the expect_by_provider.
          Still valid on its own merits, but it is no longer motivated by this cell — see
          `scope`.
